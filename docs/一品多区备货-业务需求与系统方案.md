# 一品多区备货:业务需求梳理与系统方案

> 适用范围:电商仓(10 个电商仓,单仓日均 1.5 万单、节假日翻倍,客单平均 6.7 件,299 包邮)
> 系统链路:APP(渠道)→ OMS(销售单)→ OFC(履约单)→ WHC(转发出库单/平台化 WMS)→ WMS(3PL)
> 库存模型:APP 预占中台库存(SKU 总量,与 WMS 对账,双方准确);WMS 接单不预占,分货拆单进波次后才分配库存。

---

## 0. 背景与目标

### 0.1 现状

- **一品一区**:每个 SKU 只在一个区(食品区、化学品区、AGV 区…)。拣货按区,独立包裹出库,**不在仓库集单**;集单在**物流工作站**完成(OFC 前置面单,拆单后子单运单与前置运单绑定,物流服务商在快递站聚合)——这部分生产系统已在运行。
- **拆单是确定性查表**:订单行 → SKU → 区,一一映射。
- **高峰方案**:租外仓,高流 SKU 放外仓,仍是一品一区。

### 0.2 业务诉求

**一品多区备货**:同一 SKU 同时存放在多个区。例:食品 A —— 80% 在 AGV 料箱区,20% 在人工区食品区。

### 0.3 真正要达成的目标

1. **高效正常履约**:人工区打包效率有上限,把高流量小单丢给 AGV 提吞吐与利用率。
2. **保护 AGV 吞吐**:大单(**同区 ≥30 件为大单**,走按单拣货、按单出库,原箱一件一包)不适合占用 AGV 料箱/工作站,放到人工区单独承接。
3. **减少区→区应急互补**:把大单/原箱需求**事先备在人工区**,而不是来一单就从 AGV 往人工区搬。

> 核心认知:一品多区真正的难点不是"一个 SKU 放多个库位"(WMS 库位模型天然支持),而是**"订单到底从哪个区扣减、哪个区拣货"——从"确定性拆单"变成"决策性分配"**。

---

## 1. 业务需要补充的信息

业务必须把 "80%/20%" 背后的**决策规则**讲清楚,否则系统无法落地。

| # | 信息项 | 说明 | 现状澄清 |
|---|--------|------|----------|
| 1 | **目的/目标** | 决定一切规则的优先级:提吞吐 / 保 AGV / 冗余 / 容量 | 已明确:高效履约 + 保 AGV + 减少互补货 |
| 2 | **比例的性质** | 80/20 是**补货/上架目标**(柔性)还是**硬性分配约束** | 应是**库存分布策略/补货目标**,扣减按"拣货优先级"走,二者解耦 |
| 3 | **选区优先级** | 对含该 SKU 的订单,按什么算出**唯一**优先区 | 已明确:**按订单属性驱动**——大单(同区≥30)→人工区按单拣;小单→AGV |
| 4 | **是否跨区拆行** | 同一行数量不足时拆零到两区,还是保行只取一区 | 一期走**方案B**(规则计算最终落一个区);**方案A**(跨区拆行)二期再议 |
| 5 | **包裹/成本取舍** | 多区=多包裹的取舍口径 | 已明确:包裹聚合在物流工作站/快递站已解决,下游不阻塞 |
| 6 | **SKU×区 约束** | 哪些 SKU 能进 AGV | 已明确:**上机标识**为人工维护的主数据 |
| 7 | **缺货降级** | 命中区缺货怎么办 | 已明确:**部分缺量→紧急补货;全部缺货→标记人工(沟通取消 / 人工补货发货)** |
| 8 | **KPI 口径** | 验证 80/20 是否最优:分区拣货效率、单均包裹、AGV 命中率、运费、缺拣改派率 | 待业务补充 |

**结论:业务要交付的不是"80/20"这个数字,而是上述 8 组规则。其中 #3 #4 #7 是系统能否动工的前提。**

## 2. 一品多区解决的业务问题(效率 vs 补货)

两类收益,稳健度不同,要分开看:

### 2.1 拣货效率:确定性收益

提升来源不是"同一件拣得更快",而是**订单画像与拣货模式的匹配**:

- 一品一区时,一个区被迫同时服务两类相反订单(小单适合 AGV、大单适合人工按单拣),两头照顾必有一头低效;且**一个 30 件大单丢进 AGV 会长时间霸占料箱/工作站,直接拖垮吞吐**。
- 一品多区后:80% 喂 AGV 接小单(用满设计能力)、20% 在人工区接大单。**核心是把会拖垮 AGV 的大单挡在 AGV 之外,保住吞吐与利用率。**

### 2.2 相互补货:条件性收益

- 一品多区**不消灭补货,而是改变其性质**:从"按单触发的应急区→区搬运"变为"计划性补货"。
- 区→区互补会**减少**(尤其应急搬运),前提是 80/20 按"小单/大单需求结构"分 SKU 设准、能动态调;比例设错反而 churn 更多。
- 补货转移为 **储备区/入库上架 → 分区** 的计划补货。
- **降低互补货的系统杠杆**:① 优先从共享储备区/入库上架分流补货,而非区→区互搬;② 按 SKU 动态校准比例(用 #8 指标驱动)。

## 3. 系统方案评估:决策放 WHC 还是 WMS?

### 3.1 关键约束

- **中台/OMS/OFC/WHC 全程基于 SKU 逻辑总量,不感知"区"。** 分区分配是 WMS 在"分货拆单+波次"环节的内部子问题。
- **WMS 接单不预占、波次晚绑定(late binding)是刻意设计**,为的是波次批量优化(合波、路径、设备负载均衡、就近库位)。**任何把库存提前锁死的方案都在牺牲这个核心优化**——这是评判所有路径的标尺。
- **包裹碎片化**是唯一外溢到上游的副作用,但已被"物流工作站/快递站聚合"消化。

### 3.2 核心矛盾

不可能同时满足三件事,只能取其二:

- (a) 决策在平台 WHC;(b) 不提前预占;(c) 高频下不产生大量改派。

> WHC 决策 + 不预占 → 高频热销 SKU 上决策过期 → **大面积改派,反吃掉效率**(高峰更糟)。这是该需求最大的命门。

### 3.3 三条路径对比

| 路径 | 做法 | 利 | 弊(高频下) |
|------|------|----|-----------|
| **路径1** | WMS 提供实时分区库存,**WHC 锁表预占**(账本仍在 WMS) | 决策有预占背书、不漂移、改派少;单一账本 | ① **违背晚绑定**,牺牲波次批量优化;② 热销 SKU **锁表热点/行锁竞争/死锁**,高峰更糟;③ WHC 进库存事务关键路径,跨系统同步调用=时延+强耦合+分布式事务补偿 |
| **路径2** | **WMS 自己做**(规则+执行都在 WMS) | 决策与执行同地,无时间窗、无跨系统改派,晚绑定保留,本地锁最稳最快 | **丢掉"上移平台"战略**:10 仓/多 3PL 各写一套,不一致、迭代慢、被 3PL 绑定 |
| **路径3 ✅** | **WHC 定规则、WMS 跑规则**(控制面上移、数据面本地) | 规则平台统一下发 + 运行时本地执行,**两头都要** | 增加"规则下发 + 结果回传"的决策流复杂度(可控,不触账本) |

### 3.4 推荐:路径3 —— 控制面上移、数据面本地

| 层 | 归属 | 职责 |
|----|------|------|
| **控制面(策略)** | **WHC(平台,上移)** | 持有并**版本化下发**分区分配策略(优先级、大单阈值、区偏好、80/20 比例目标、上机标识联动、缺货降级);**不做每单实时分配、不预占、不记账** |
| **数据面(执行)** | **WMS(3PL,本地)** | 用平台下发的规则 + 本地实时分区库存&设备负载,做**波次晚绑定 + 库位绑定 + 顺位改派 + 补货**;结果回传 WHC/OFC |

**上移的是"规则定义权 + 跨仓标准化 + 可视化",不是"实时账与实时运算"。**
战略目标(10 仓一套规则、快速迭代、弱化 3PL 锁定)拿到;高频下的时间窗/锁竞争/改派 churn 全部避开,因为决策回到与库存、设备同地的 WMS。

## 4. 库存账本:为什么 WHC 不记账

### 4.1 核心原则:**只能有一份权威库存账本 = WMS**

"复杂度爆炸"的根因是**双权威账本**:WHC 若维护一份分区库存、随每笔订单/拣货/补货/盘点实时加减并与 WMS 对齐,第二本账**一定漂移**,陷入无止境对账。

### 4.2 为什么本场景 WHC 无需实时账本

- **选区主要由订单属性(大单/小单)驱动,对库存新鲜度弱依赖**;库存只在边界场景(目标区明显不够)用于兜底裁量,且最终裁量在 WMS。
- 即使 WHC 的只读快照过期,**WMS 在库位级终绑 + 顺位改派会自动纠偏**,正确性不依赖 WHC 快照实时性。

### 4.3 账本归属

| | 角色 | 库存关系 |
|---|------|---------|
| **WHC** | 出"建议区 + 优先级序列"(策略) | **只读** WMS 周期同步的分区可用快照;**不持权威账、不加减** |
| **WMS** | 波次终绑到库位 + 改派 + 补货 | **唯一权威账本**,所有加减只发生在此,精确到库位 |

> WHC 与 WMS 是 "区级建议 vs 库位级权威" 的**层级关系,不是两本账的对账关系**——所以不冲突、不增加账本复杂度。增加的只是"路由决策流"复杂度,这是上移规则必付且可控的代价。

## 5. 行业最佳实践

### 5.1 解决的业务问题

1. **拣选效率/自动化利用率最大化**:每类订单导到最合适的拣选资源(订单分流 order streaming)。
2. **设备产能天花板与削峰**:自动化有吞吐上限,把对的订单结构喂给它、其余溢出到人工/外仓,避免高峰瓶颈。
3. **储位/库容现实**:料箱储位贵且小,高流 SKU 全量塞不进料箱,必须"自动化放周转量 + 储备/溢出放便宜储区"。
4. **业务连续性**:自动化停机时人工区仍能履约。

### 5.2 系统方案通行构件

1. **Slotting 引擎(库存分布策略)**:按动销(ABC)、订单画像、体积、预测,算出每个 SKU 在各储区放多少——**80/20 应是它的输出,而非手拍常数**;周期跑 + 动态微调。
2. **订单画像 & 波次分流(order streaming)**:波次前对订单分类(单件/多件小单/大单/整箱),各导向对应拣区。**在有实时库存+设备状态的 WMS/WES 层做**——必须"库存感知 + 设备负载感知",这正是不能放远端平台层的根因。
3. **晚绑定分配 + 改派**:波次释放软分配,拣货确认绑库位,缺货顺位改派。
4. **前置区补货引擎**:min/max 或需求驱动,**从储备区→拣区**补货(而非区→区互搬),按水位 + 预期波次需求触发(波次预补)。
5. **职责分层**:OMS/中台/DOM 只做**跨仓寻源**(基于 SKU 聚合可用量 ATP,不下探到区);**仓内分区分配是 WMS/WES 的事**。

### 5.3 行业结论

**仓内一品多区的实时分配放在 WMS/WES 层,不放订单/平台层。** 本案的特殊性仅是"WMS 是 3PL 的、想要平台管控",标准解法就是**路径3:策略集中到平台并下发,运行时分配留在本地执行**(控制面/数据面分离),用于多仓、多 3PL 标准化而不牺牲运行时性能。

## 6. WHC ↔ WMS 接口设计(路径3)

### 6.1 规则下发(WHC → WMS,控制面,低频/版本化)

```
RuleSetPublish {
  ruleSetVersion        // 规则版本号,幂等
  effectiveTime         // 生效时间
  warehouseScope[]      // 适用仓
  zonePriorityRules[]   // 选区优先级规则(条件 → 区优先级序列)
  bigOrderThreshold     // 大单阈值(默认:同区 ≥30 件)
  splitLineAllowed      // 是否允许跨区拆行(一期=false)
  ratioTargets[]        // {sku/category, zone, targetRatio} 比例目标(补货/Slotting 用)
  onMachineFlagBinding  // 上机标识联动规则
  fallbackPolicy        // 缺货降级:partialShort→紧急补货;fullShort→标记人工
}
```

### 6.2 拆单/分配(WHC 出建议,WMS 终裁)

- **WHC 输出**:子单 + **建议区 + 优先级序列**(不是锁死的单一区),基于规则 + 只读分区快照。
- **WMS 执行**:按优先级序列,用本地实时库存&设备负载做波次晚绑定;命中不了首选则**按序列顺位改派,改派在 WMS 内闭环,不跨系统、不回 WHC**。

```
AllocationSuggestion (WHC→WMS) {
  fulfillmentOrderId
  lines[] { sku, qty, zonePrioritySeq[] }   // 每行的区优先级序列
  ruleSetVersion
}
```

### 6.3 结果回传(WMS → WHC,用于可视/对账/KPI)

```
AllocationResult (WMS→WHC) {
  fulfillmentOrderId
  packages[] { zone, sku, qty, locationBound, reassigned(bool) }
  shortMarks[] { sku, shortQty, action(replenish/manual) }
  ruleSetVersion
}
```

### 6.4 分区库存快照(WMS → WHC,只读,周期/事件)

```
ZoneStockSnapshot (WMS→WHC) {
  warehouseId, snapshotTime
  items[] { sku, zone, available }   // 仅供 WHC 算优先级边界裁量,非权威账
}
```

> 同步频率:够算优先级即可(常态属性路由对其弱依赖),建议分钟级 + 低水位事件推送;**严禁让 WHC 据此做加减记账**。

## 7. 分期落地

| 阶段 | 范围 | 风险 |
|------|------|------|
| **一期(MVP)** | 比例仅作 Slotting/补货目标;**默认不跨区拆行(方案B)+ 包裹最小化**;WHC 下发规则 + WMS 执行/改派;分区盘点保精度;缺货按 #7 降级 | 低:上游零改动,不放大包裹碎片化,即拿 AGV 吞吐收益 |
| **二期** | 按销量**动态调比例**;引入**方案A 跨区拆行**(受成本门槛约束);补货引擎自动化;#8 KPI 看板驱动比例迭代 | 中:方案A 对分区实时性要求上升,仍由 WMS 持账、WHC 拿更高频只读视图 |
| **削峰延伸** | 把**外仓建模成一个特殊的"区"**,用同一套分配/改派逻辑统一管理,替代"临时租仓单独一套" | —— |

### 兜底(3PL WMS 改不动时,退路径1,过渡用)

- **只预占稀缺区**(临近见底的区),充裕的 AGV 区仍走 WMS 晚绑定不锁;
- **按"区聚合"预占,不锁到库位**(减少锁行);乐观并发 + 短 TTL + 超时自动释放/补偿;
- **仅当区跨低水位线时才走预占**,常态纯属性路由不预占;
- 定位为过渡,目标仍是迁回路径3。

---

## 8. 一句话收口

> **业务上**:把"80/20"翻译成 8 组规则(目标/比例性质/选区优先级/是否拆行/包裹取舍/SKU×区约束/缺货降级/KPI)。
> **系统上**:采用**路径3——WHC 定规则、WMS 跑规则,控制面上移、数据面本地**。WHC 只读、出优先级序列、不记账;WMS 单一权威账、库位终绑、负责所有加减与改派。既拿到"核心能力上移平台 + 10 仓标准化"的战略收益,又规避双账本复杂度与高频改派 churn,符合行业最佳实践。
